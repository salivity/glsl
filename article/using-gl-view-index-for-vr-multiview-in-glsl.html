Using gl_ViewIndex for VR Multiview in GLSL

This article explores how the gl_ViewIndex built-in variable in GLSL streamlines Virtual Reality (VR) rendering through hardware-accelerated multiview techniques. Multiview rendering allows a single draw call to render a scene simultaneously from multiple viewpoints—typically the left and right eyes in VR—drastically reducing CPU submission overhead. Below, we examine the mechanics of gl_ViewIndex, how it integrates into shader pipelines, and why it is essential for achieving high frame rates in immersive applications.

The VR Rendering Problem

Standard stereoscopic VR requires rendering the same 3D scene twice, once for each eye's perspective. Traditional approaches achieve this via:

  1. Sequential Draw Calls: Rendering the entire scene for the left eye, switching render targets or viewports, and repeating the process for the right eye. This doubles CPU draw calls, driver overhead, and state changes.
  2. Geometry Instancing: Drawing instances of geometry and routing them to target viewport slices. While this reduces CPU overhead, it introduces GPU vertex processing overhead and complex vertex-to-primitive routing.

Multiview extensions—such as GL_OVR_multiview, GL_OVR_multiview2 in OpenGL/OpenGL ES, and VK_KHR_multiview in Vulkan—resolve this by allowing the GPU to process draw calls once and replicate geometry across multiple render targets (typically a 2D texture array) inside the graphics pipeline.

The Role of gl_ViewIndex

The gl_ViewIndex built-in input variable acts as the primary switch in GLSL to differentiate between render views. When a multiview render pass executes, the graphics driver broadcasts primitives to the designated number of views (for stereo VR, this count is 2).

Inside the shader, gl_ViewIndex is an integer that indicates the specific view currently being processed:

  • 0: Typically corresponds to the left eye.
  • 1: Typically corresponds to the right eye.

Because each view requires unique transformation parameters (such as the eye position, view matrix, and projection matrix), shaders use gl_ViewIndex to dynamically index into uniform arrays or Uniform Buffer Objects (UBOs).

Implementing gl_ViewIndex in a Vertex Shader

In a typical multiview vertex shader, the matrices for both eyes are bundled together. gl_ViewIndex indexes these matrices to compute the correct clip-space coordinates for the current eye:

#version 300 es
#extension GL_OVR_multiview2 : require

layout(num_views = 2) in;

layout(location = 0) in vec3 a_Position;

// Array containing View-Projection matrices for [0] Left Eye and [1] Right Eye
uniform mat4 u_ViewProjection[2];
uniform mat4 u_Model;

void main()
{
    vec4 worldPosition = u_Model * vec4(a_Position, 1.0);
    
    // Select the matrix corresponding to the current eye view
    gl_Position = u_ViewProjection[gl_ViewIndex] * worldPosition;
}

Execution Across Shader Stages

While primarily utilized in the vertex stage for geometric transformation, gl_ViewIndex is also accessible in fragment shaders (depending on extension support, such as GL_OVR_multiview2 or standard Vulkan multiview):

  • Vertex Shading: Calculates view-dependent clip coordinates (gl_Position), camera-relative vectors, and lighting directions.
  • Fragment Shading: Evaluates view-dependent effects, such as specular highlights, eye-specific reflections, or stereoscopic user interface elements.

The underlying hardware routes the output of the fragment shader directly to the corresponding slice of the 2D texture array bound as the multiview framebuffer target.

Performance Benefits for VR

Using gl_ViewIndex yields major performance improvements essential for VR's strict 90Hz+ refresh rate requirements:

  • CPU Overhead Reduction: The host application submits a single draw call rather than two, halving driver validation, draw call loops, and pipeline re-bindings.
  • Primitive Processing Efficiency: Modern GPU hardware can share initial vertex processing stages across both views before branching on gl_ViewIndex, optimizing memory bandwidth.
  • Deterministic Cache Utilization: Because both eye perspectives share resource state, texture and geometry data remain hot in the GPU L1 and L2 caches during execution.
