GLSL Float to Int Conversion Performance Cost

Converting between floating-point and integer types in GLSL introduces a measurable performance cost that varies from negligible to severe depending on shader complexity and target GPU architecture. While modern graphics hardware includes dedicated hardware support for format conversions, executing cast operations consumes Arithmetic Logic Unit (ALU) cycles, increases register pressure, and can stall instruction pipelines. This article breaks down how type conversion operates at the hardware level, its impact on instruction throughput across desktop and mobile architectures, and how to minimize conversion overhead in shader pipelines.

Hardware Mechanics of GLSL Type Conversion

In GLSL, conversions between float, int, and uint are never purely syntactic; they require physical data translation at the instruction set architecture (ISA) level. Floating-point values conform to the IEEE 754 standard (sign bit, exponent, mantissa), whereas signed integers use two's complement representation.

Because the bit arrangements represent entirely different mathematical constructs, the GPU must actively recalculate the value:

  • Float-to-Integer (int(val) or uint(val)): The ALU extracts the mantissa, shifts it based on the exponent, truncates fractional values, applies sign adjustments, and clamps the result to prevent integer overflow. At the ISA level, this is dispatched as instructions like F2I or F2U (NVIDIA) or V_CVT_I32_F32 (AMD).
  • Integer-to-Float (float(val)): The ALU normalizes the integer value into a fraction and computes the corresponding exponent. This maps to instructions like I2F or V_CVT_F32_I32.

Both operations require full ALU processing stages. They are not zero-cost bit reinterpretations. For direct bitwise manipulation without mathematical conversion, GLSL provides functions like floatBitsToInt() and intBitsToFloat(), which frequently compile down to zero-cost register moves or simple aliasing on modern unified architectures.

Throughput and Cycle Latency

On modern desktop GPUs (NVIDIA Turing/Ampere/Ada, AMD RDNA 2/3), format conversion instructions generally run on the primary single-precision floating-point (FP32) or integer (INT32) execution pipelines:

  • Instruction Throughput: On most unified architectures, a conversion instruction (F2I / I2F) has the same throughput as a standard FP32 addition or multiplication (typically 1 instruction per clock cycle per execution lane). However, using a conversion operation consumes an issue slot that could have executed a functional mathematical operation, effectively halving the arithmetic efficiency of that cycle.
  • Vectorized Conversions: GLSL operations such as ivec4(myVec4) convert four scalar values. Because modern GPUs utilize scalar ALUs inside a SIMD/SIMT warp or wavefront, converting a vec4 to an ivec4 dispatches four individual conversion instructions per thread, scaling the cycle overhead linearly.
  • Dependent Texture Fetches: Converting a computed floating-point coordinate to an integer for texelFetch() creates an instruction dependency. If the conversion latency cannot be hidden by other independent math instructions in the shader, the warp stalls while awaiting the integer result.

Architectural Discrepancies: Desktop vs. Mobile

The performance penalty of ALU conversions is significantly more pronounced on mobile and embedded chipsets (such as ARM Mali, Qualcomm Adreno, and Imagination PowerVR) compared to desktop hardware:

  1. Dedicated vs. Shared Datapaths: Desktop architectures feature deep execution pipelines that hide conversion latencies via massive thread-level parallelism. Mobile architectures often have asymmetric ALUs where conversion instructions must execute on specific sub-pipes, creating resource contention.
  2. Precision Qualifiers: Mobile GPUs heavily optimize for half-precision (mediump float and mediump int). Converting between a full-precision highp float (32-bit) and a mediump int (16-bit) triggers both a format conversion and a precision-packing step, incurring higher cycle penalties than homogeneous 32-bit operations.

Best Practices to Mitigate Conversion Costs

  • Domain Consistency: Maintain calculations in a single domain as long as possible. If an algorithm relies heavily on integer operations (e.g., bitwise hash generation, procedural voxel traversal), compute the logic entirely using uint or int rather than switching back and forth between float and int.
  • Bit-Casting for Raw Storage: When packing arbitrary data into textures or buffers, use floatBitsToUint() and uintBitsToFloat() instead of explicit arithmetic casts. Bit-casts preserve raw bits without driving arithmetic transformation logic.
  • Pre-computation: Hoist conversions out of high-frequency loops and fragment shaders. Uniform data or vertex attributes should be uploaded in the exact numerical format expected by the core computation rather than converted dynamically per-vertex or per-fragment.
