Why Older GLSL Forbade Array Equality Comparisons

In early versions of the OpenGL Shading Language (GLSL), developers were prohibited from comparing entire arrays using the equality (==) and inequality (!=) operators. This article explains why the restriction existed, focusing on early graphics hardware constraints, performance considerations regarding deep value comparisons, compiler complexity across varied GPU drivers, and the historical classification of arrays as second-class types in early shading pipelines.

Early GPU Architecture and Instruction Constraints

Early graphics processors were fundamentally vector processors built to process floats, vectors, and matrices with direct instruction mapping. Operations like adding a 4-component vector or taking a dot product corresponded to single-cycle assembly instructions.

Arrays, conversely, do not have dedicated single-cycle comparison instructions in GPU instruction set architectures (ISAs). Evaluating whether two arrays are equal requires evaluating every element sequentially or via unrolled comparison chains. Early hardware lacked sophisticated branch prediction, unified shader cores, and unified memory subsystems, making bulk multi-register operations inefficient to implement at the hardware level.

Prevention of Costly Implicit Operations

Shading languages prioritize real-time performance and predictable execution times. In GLSL, an operation like a == b for primitive types (such as float, vec3, or mat4) executes quickly with minimal machine instructions.

If array comparisons were supported natively, evaluating arrayA == arrayB on large arrays would require:

  • Full unrolling of comparisons across all indices.
  • Extensive temporary register allocation to hold intermediate boolean flags.
  • Substantial instruction cache expansion.

By omitting native array equality, the Khronos Group prevented developers from unknowingly introducing massive register pressure or instruction stalls through what appeared syntactically to be a single, lightweight operation.

Arrays as Second-Class Citizens

In older specifications (such as GLSL 1.10, 1.20, and GLSL ES 1.00), arrays were treated as second-class data structures rather than first-class types. They were subject to severe syntactic and semantic limitations:

  • Arrays could not be returned from functions.
  • Dynamic indexing was heavily restricted, often requiring constant or loop-index-only access depending on whether the array was a uniform or temporary variable.
  • Whole-array assignments were either forbidden or inconsistently supported across hardware vendors.

Because arrays lacked full type parity with basic GLSL data types, operators that relied on value-level identity—such as == and !=—were naturally excluded from the language grammar.

Compiler and Driver Complexity

In the early eras of programmable shaders, GPU vendors shipped their own GLSL compilers embedded directly inside the graphics driver. Divergent interpretations of ambiguous specifications frequently led to driver crashes, compile failures, or platform-specific rendering artifacts.

Requiring drivers to generate control flow or unroll logic for deep component-wise array comparisons added significant complexity to driver compiler front-ends. Restricting array equality kept the specification simple and minimized the surface area for compiler bugs on fragmented hardware targets.

Evolution in Later Specifications

As graphics pipelines transitioned to fully unified, compute-capable architectures, the hardware limitations that originally justified the restriction disappeared. Starting with GLSL 1.30 (desktop) and later GLSL ES revisions, the language elevated arrays to first-class types. Arrays gained support for implicit copying, passing and returning from functions, and equality checking, executing deep component-wise comparisons automatically.
