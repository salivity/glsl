Hardware Primitive Culling with gl_CullDistance in GLSL

This article explores the role of the built-in GLSL array gl_CullDistance in evaluating and utilizing hardware-accelerated primitive culling without triggering geometric vertex clipping. By examining the fundamental differences between clipping and culling stages in the OpenGL pipeline, you will understand how gl_CullDistance provides an efficient, all-or-nothing primitive rejection mechanism that preserves original geometry topology and aids in performance profiling.

In standard programmable graphics pipelines, custom geometry rejection against user-defined planes typically relies on gl_ClipDistance. When a primitive intersects a plane defined via gl_ClipDistance, the hardware clipper must interpolate vertex attributes and generate new vertices to reconstruct a clipped polygon. While geometrically accurate, this introduces computational overhead, dynamic topology changes, and bandwidth consumption in the primitive assembly stage.

The introduction of gl_CullDistance provides an explicit pathway to bypass the clipping step in favor of primitive-level culling. Defined as an array of floating-point values output by the vertex, tessellation, or geometry shader, gl_CullDistance assigns a scalar distance metric to each vertex relative to a culling plane or bounding volume.

The hardware culling rule dictates that if a single cull distance metric is less than zero across all vertices comprising a given primitive (point, line, or triangle), the hardware immediately discards the entire primitive before rasterization. Conversely, if at least one vertex evaluates to a value greater than or equal to zero, the entire primitive is retained and rasterized as-is, without generating new clipped edges or vertices.

Using gl_CullDistance to test hardware primitive culling provides several key architectural and diagnostic advantages:

  • Zero Topology Modification: Because primitives are rejected entirely rather than intersected, the pipeline maintains strict vertex-to-primitive ratios. This allows developers to isolate and benchmark primitive culling throughput without introducing the variable cost of clipping algorithms.
  • Deterministic Pipeline Workloads: Traditional clipping results in fluctuating primitive and vertex counts that can confound GPU profiling. Testing with gl_CullDistance ensures that primitive rates either stay identical or drop cleanly, revealing the true efficiency of fixed-function culling blocks.
  • Low-Overhead Custom Visibility: Shaders can compute custom visibility checks—such as distance-based Level of Detail (LOD) cutoffs, sphere or box bounds, and specialized frustum planes—and offload the actual rejection phase directly to hardware fixed-function culling units instead of managing complex geometry shader dispatches or compute-shader compaction passes.

To enable this functionality in OpenGL, specific cull distance planes must be explicitly activated using glEnable(GL_CULL_DISTANCE0 + i). If both gl_ClipDistance and gl_CullDistance are combined, the hardware processes culling first; any primitive completely culled by gl_CullDistance avoids the clipping stage entirely.

By leveraging gl_CullDistance, developers can effectively stress-test the hardware's native rejection capabilities, simulate coarse-grained culling volumes at the vertex level, and eliminate the performance variance typically caused by vertex clipping operations.
