How GLSL Compilers Perform CSE on Complex Formulas

This article examines how modern GLSL (OpenGL Shading Language) compilers detect and eliminate redundant calculations in complex mathematical expressions. It details the step-by-step optimization pipeline, covering parsing into Intermediate Representation (IR), Static Single Assignment (SSA) form, expression hashing via Global Value Numbering (GVN), control-flow validation, and the architectural trade-offs between register allocation and recomputation on GPU hardware.

1. Translation to SSA Intermediate Representation

A GLSL compiler does not execute optimizations directly on raw GLSL source text. Instead, the front-end parses the code into an Abstract Syntax Tree (AST) and lowers it into a lower-level Intermediate Representation (IR), such as SPIR-V or a driver-internal IR (e.g., Mesa's NIR or LLVM-based IRs in proprietary drivers).

During this lowering, code is converted into Static Single Assignment (SSA) form. Under SSA, every variable is assigned exactly once. This eliminates variable shadowing and reassignments, turning mutable code into a directed acyclic graph (DAG) of pure operations where data dependencies become mathematically transparent.

2. Canonicalization of Complex Math

Before identical operations can be identified, the compiler normalizes expressions into canonical forms. Complex formulas often contain mathematically equivalent expressions written in different ways. Canonicalization handles:

  • Commutativity: Ensuring a + b and b + a, or x * y and y * x, share identical operand ordering (typically sorted by unique SSA IDs).
  • Associativity and Constant Folding: Grouping constants together so that (x + 2.0) + 3.0 simplifies to x + 5.0.
  • Algebraic Equivalences: Replacing negations or subtractions with standard representations (e.g., converting a - b to a + (-b)).

3. Scalarization and Swizzle Unpacking

GLSL heavily relies on vector types (vec2, vec3, vec4) and matrix operations. Redundancies often hide across vector components—for example, computing dot(v.xy, v.xy) alongside a separate calculation of v.x * v.x.

Modern GPU compilers frequently perform scalarization, breaking vectors into individual scalar SSA operations. The compiler tracks individual components and swizzles, allowing it to detect common subexpressions embedded within different vector operations. Once decomposed, identical scalar sub-components are matched even if they originated from different vector lanes.

4. Global Value Numbering (GVN)

The core engine for Common Subexpression Elimination (CSE) in complex formulas is Global Value Numbering (GVN):

  1. Hash Lookup: As the compiler traverses the SSA graph, it computes a deterministic hash for each instruction based on the opcode and the value numbers of its inputs.
  2. Lookup Table: The compiler checks a scoped lookup table. If a matching hash exists, the current operation is redundant.
  3. Replacement: The redundant expression is deleted, and all subsequent instructions referencing its result are updated to point to the previously computed value.

For transcendental functions (sin, cos, pow, sqrt), the compiler matches the operation directly provided the fast-math flags allow it (i.e., when strict IEEE-754 precision constraints are relaxed, which is standard in graphics rendering).

5. Control Flow and Dominance Trees

In complex shaders containing branches and loops, subexpressions can only be eliminated if the earlier computation is guaranteed to execute before the later one. The compiler builds a Dominator Tree from the Control Flow Graph (CFG):

  • A basic block \(A\) dominates block \(B\) if every execution path to \(B\) must pass through \(A\).
  • Local CSE eliminates duplicates within the same basic block.
  • Global CSE eliminates duplicates across different blocks only if the initial computation dominates all subsequent uses.
  • If identical computations occur in parallel branches, the compiler may hoist the common subexpression above the branch into an immediate dominator block.

6. The Hardware Balance: Register Pressure vs. Rematerialization

Eliminating a common subexpression requires storing its result in a register until its last use. In GPU architectures, high register usage directly limits occupancy—the number of active warps or wavefronts a Compute Unit can execute simultaneously to hide memory latency.

If an expression is cheap to compute (such as a simple fused multiply-add, fma) and keeping its value alive would extend its live range across hundreds of instructions, the compiler may perform rematerialization instead. In these cases, the compiler deliberately bypasses CSE or re-evaluates the expression locally to keep register pressure low and preserve overall GPU throughput.
